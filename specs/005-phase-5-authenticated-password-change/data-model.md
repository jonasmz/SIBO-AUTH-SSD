# Data Model: Authenticated Password Change

Phase 5 adds **no table, column, index or migration**. It changes existing Identity user data
through Identity and extends one enumeration used by the Phase 4 session family.

## Existing entity: ApplicationUser (Identity)

| Field | Change by a successful password change |
|---|---|
| `PasswordHash` | Replaced by `UserManager.ChangePasswordAsync`. |
| `SecurityStamp` | Regenerated by Identity as part of the same call. |
| `ConcurrencyStamp` | Regenerated by Identity's `UpdateAsync`. |
| `Email`, `UserName`, `IsEnabled`, roles, lockout fields, `AccessFailedCount` | Unchanged. |

- An incorrect current password changes only `AccessFailedCount` (and, at the configured
  threshold, `LockoutEnd`) through `UserManager.AccessFailedAsync`, as SRS NFR-SEC-BF-001 requires
  ([research.md §3](research.md)). The credential and sessions are unchanged.
- Every other failed change (refusal or error) changes no field.
- `DatabaseInitializer.BootstrapAsync` returns early when the administrator row exists, so neither
  startup nor migration restores the initial `admin` password (SRS NFR-SEC-ADMIN-003). Phase 5
  keeps that behavior and adds a restart test for it.
- Password hash, security stamp and Identity error descriptions never appear in responses or logs.

## Existing entity: RenewableSessionFamily (Phase 4)

| Field | Change |
|---|---|
| `RevokedAtUtc` | Set once, from `TimeProvider`, on every active family of the user except the kept one. |
| `RevocationReason` | `PasswordChanged` on those families. |

### Enumeration: SessionRevocationReason

`Replay = 0`, `Logout = 1`, `UserDisabled = 2`, `Administrator = 3`, **`PasswordChanged = 4`**
(appended). Stored as `int?`; existing values keep their numbers; no schema change.

### Kept family (current session)

The family is kept only when all of the following hold for the presented `auth_refresh` value:

1. It passes `RefreshCredentialProtector.TryHash` (well-formed 256-bit base64url).
2. Its digest matches a `RefreshCredential` that is not consumed, not revoked and not expired.
3. That credential's family is active (`IsActive(now)`) and its `UserId` equals the token `sub`.

Otherwise no family is kept. The kept family and its credentials are never modified by this
operation. `RefreshCredential` rows are not modified by Phase 5 at all: family revocation alone
makes every chain member unusable (Phase 4 rule).

## State transitions

```text
change-password request (valid bearer token)
  │
  ├─ invalid body ─────────────────────────────► 400   (no transaction)
  ├─ not ready ────────────────────────────────► 503   (no transaction)
  │
  └─ BEGIN serializable
       ├─ user not found ─────────────────────► rollback → 401
       ├─ resolve kept family (read only)
       ├─ ChangePasswordAsync
       │    ├─ PasswordMismatch ─► AccessFailedAsync → COMMIT counter only → 401
       │    ├─ Password* policy errors ───────► rollback → 400 (policy)
       │    └─ other failure ─────────────────► rollback → 400 (invalid request)
       ├─ revoke active families ≠ kept (PasswordChanged)
       ├─ COMMIT ─── DbException/DbUpdateException ► rollback → 503
       └─ log security event ─────────────────► 204
```

Families already revoked or expired are left as they are. A concurrent refresh that consumed the
presented credential first makes it unusable here, so its family is revoked too (fail-safe).

## Application-layer types (feature `Passwords`)

| Type | Shape | Notes |
|---|---|---|
| `ChangePasswordCommand` | `UserId`, `CurrentPassword`, `NewPassword`, `PresentedRefreshTokenHash?` (`byte[]?`) | Built by the endpoint from `sub`, body and cookie. Not logged. |
| `ChangePasswordOutcome` | enum: `Changed`, `InvalidCurrentPassword`, `InvalidNewPassword`, `Invalid` | `InvalidCurrentPassword` also covers an unknown subject. |
| `IPasswordChange` | `Task<ChangePasswordOutcome> ChangeAsync(ChangePasswordCommand, CancellationToken)` | Implemented by `Infrastructure/Identity/PasswordChange`. |

## Validation rules

| Rule | Owner |
|---|---|
| Body is JSON with non-blank `currentPassword` and `newPassword` | API request (`ChangePasswordRequest.IsValid`), same convention as `LoginRequest` |
| Current password correct | Identity (`ChangePasswordAsync`); a mismatch is counted with `AccessFailedAsync` |
| New password satisfies policy | Identity password validators, configured via the `Identity` section |
| Account target | Only the token `sub`; the body has no identifier field and unknown fields (e.g. `userId`, `email`) are ignored |
