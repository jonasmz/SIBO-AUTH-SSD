# Phase 0 Research: Password Recovery, Reset and Email

All planning questions are resolved below. There are no remaining `NEEDS CLARIFICATION` items.
Version facts were checked on 2026-10-08 against the installed .NET 10.0.12 shared framework and the
public NuGet and Docker Hub registries.

## 1. Reset token generation and validation

**Decision**: Register only Identity's `DataProtectorTokenProvider<ApplicationUser>` under
`TokenOptions.DefaultProvider` (`AddTokenProvider<…>(TokenOptions.DefaultProvider)` on the existing
`AddIdentityCore` builder). Generate with `UserManager.GeneratePasswordResetTokenAsync` and reset
with `UserManager.ResetPasswordAsync`. Keep Identity's default token lifetime
(`DataProtectionTokenProviderOptions.TokenLifespan`, one day) and add no setting for it.

**Rationale**: SRS FR-PWD-005/008–011 and Constitution V require Identity's own mechanism. The
data-protected token embeds the creation time, user id, purpose and security stamp, so it is
temporary (FR-PWD-008), bound to one account, rejected when altered (FR-PWD-010), and invalidated
when the security stamp changes (FR-PWD-009) — which `ResetPasswordAsync` and the Phase 5
`ChangePasswordAsync` both do. Therefore a token is single-use without any token store (NFR-003).
`ResetPasswordAsync` verifies the token before validating the new password, so the policy result is
never observable without a valid token. `AddDefaultTokenProviders()` was not used because it also
registers email, phone and authenticator providers that no capability needs (Constitution IV).

**Alternatives considered**: A custom or persisted token was rejected (Technical Constraints §8
prohibits manual reset-token generation; NFR-003 prohibits a token store). Binding the token
lifetime to a new configuration key was rejected because the spec assumption keeps Identity's
lifetime and forbids a new lifetime rule.

## 2. Deterministic expiry testing

**Decision**: In the expiry scenario, the test host sets
`DataProtectionTokenProviderOptions.TokenLifespan` to a negative value (for example −1 minute)
through `ConfigureTestServices`. Tokens generated by that host are already past their validity, so
the reset is rejected without any wait.

**Rationale**: Reflection over the installed `Microsoft.AspNetCore.Identity` 10.0.12 shows that
`DataProtectorTokenProvider<TUser>` takes only `IDataProtectionProvider`, its options and a logger —
no `TimeProvider` — and compares against the system clock. A negative lifespan makes the comparison
deterministic (NFR-002, Constitution VI) and changes only test configuration, not product code.
This satisfies Roadmap §12.6 "reset token vencido cuando pueda probarse".

**Alternatives considered**: `ControlledTimeProvider` cannot reach the provider. Sleeping past a
short lifespan is prohibited. Subclassing the provider to inject time was rejected as custom token
logic.

## 3. Persistent Data Protection key ring

**Decision**: Call `AddDataProtection().PersistKeysToFileSystem(new DirectoryInfo(keysPath))
.SetApplicationName("Authentication.Api")` in Infrastructure. `keysPath` comes from the new required
setting `DataProtection:KeysPath`. At startup, fail fast with the existing `Require` pattern unless
the directory exists and is writable (create a probe file, then delete it). Compose bind-mounts
`${AUTH_DATAPROTECTION_HOST_PATH:?…}` to `/var/lib/auth-api/dataprotection`; the reference layout is
Technical Constraints §30 (`/srv/auth-system/dataprotection`). Keys are not encrypted at rest: the
host directory is owned by the container user (`APP_UID`), mode `0700`, as Technical Constraints §38
requires. The framework's startup warning about the missing XML encryptor is expected and
documented.

**Rationale**: SRS NFR-DP-001–007 and Roadmap §12.3: keys outside the container layer, a
configurable location, a lifecycle independent of Compose (bind mount, so `docker compose down -v`
cannot remove it), no external service. A fixed application name keeps the key ring isolated and
stable when the content root or container changes, so a still-valid token survives restart,
rebuild and recreation (NFR-DP-002, spec US4). Failing fast avoids discovering an unwritable
directory only at the first recovery request.

**Alternatives considered**: A named or Compose-managed volume was rejected by NFR-DP-005/006 and
Roadmap §12.3. An `external: true` volume is permitted by the roadmap as an alternative and is
documented but not used as the reference. Persisting keys in SQLite was rejected: it mixes the
cryptographic material into the database backup scope without a requirement. Certificate-based key
encryption (`ProtectKeysWithCertificate`) was rejected for now: it adds a certificate and its
lifecycle as a new secret that no requirement demands; filesystem permissions are the baseline
control. Azure/Redis key stores are prohibited.

## 4. Email port and placement

**Decision**: Application slice `Features/PasswordRecovery` defines `IEmailSender` with
`Task<bool> SendAsync(EmailMessage message, CancellationToken)` and `EmailMessage(ToAddress,
Subject, TextBody)`. `ForgotPasswordHandler` composes the single plain-text recovery message
(fixed English subject and body that contain the token and tell the user to submit it with their
email to `POST /api/auth/reset-password`) and calls the port. The return value is `false` on any
delivery failure; the handler ignores it because the caller must not observe failures. The MailKit
adapter `Infrastructure/Email/SmtpEmailSender` is the only implementation.

**Rationale**: SRS NFR-MAIL-001/002 and Technical Constraints §16.1: a minimal Application port;
the provider is not business logic, while the content of the recovery message is. A `bool` result
lets the adapter, which knows the SMTP details, log safe diagnostics while Application (which has
no logging dependency today) stays provider-agnostic. Plain text with no templating satisfies
NFR-003. The name follows the technical baseline's conceptual `IEmailSender`; it lives in the
project namespace and does not collide with Identity's generic `IEmailSender<TUser>`, which is not
used.

**Alternatives considered**: Identity's `IEmailSender<TUser>` was rejected because it belongs to
the Identity API endpoints/UI model and would put an Identity type in Application. Throwing a
delivery exception through Application was rejected because Application would then have to log or
re-map provider failures. A template engine was rejected by NFR-003.

## 5. SMTP adapter and configuration

**Decision**: Add `MailKit` **4.18.0** (published 2026-09-13; MimeKit 4.18.0 transitively; no
advisories listed on NuGet) to `Directory.Packages.props` and reference it from Infrastructure
only. `SmtpEmailSender` creates a `SmtpClient` per message: `ConnectAsync(host, port, security)`,
`AuthenticateAsync` only when a username is configured, `SendAsync`, `DisconnectAsync(true)`. No
`ProtocolLogger` is attached. The request's `CancellationToken` is passed through; MailKit's default
timeout applies. Required settings, validated at startup and never echoed:

| Setting | Rule |
|---|---|
| `Smtp:Host` | non-blank |
| `Smtp:Port` | integer 1–65535 |
| `Smtp:Security` | `None`, `StartTls` or `SslOnConnect` (maps to `SecureSocketOptions`) |
| `Smtp:Username` / `Smtp:Password` | both blank, or both non-blank |
| `Smtp:SenderAddress` | valid email address |
| `Smtp:SenderName` | non-blank |

**Rationale**: Technical Constraints §16.2–16.3 mandate MailKit as an Infrastructure adapter and
list exactly these settings; Constitution IV requires the package to serve the active phase. 4.18.0
is the newest release at least two weeks old (4.18.1 was published 2026-09-27). `Auto` and
`StartTlsWhenAvailable` are excluded because they can silently fall back to plaintext; the operator
chooses explicitly. Credentials come only from external configuration (NFR-MAIL-004,
NFR-CONFIG-002). A client per message keeps the adapter stateless and avoids connection-lifetime
infrastructure.

**Alternatives considered**: `System.Net.Mail.SmtpClient` is prohibited (TC §16.2). MailKit 4.18.1
was rejected as too recent. A pooled or background sender, a queue and retries were rejected by
NFR-003. A new timeout setting was rejected as configuration no requirement asks for.

## 6. Delivery failure handling and the generic response

**Decision**: `SmtpEmailSender` catches every exception except `OperationCanceledException`, logs
one `Warning` event (`EmailDeliveryFailed`: exception type name, SMTP status code when the
exception is `SmtpCommandException`, configured host and port, UTC time, trace/span ids) and
returns `false`. It never logs the recipient, subject, body, username or password. The
forgot-password endpoint answers the generic `204` whether delivery succeeded or not.

**Rationale**: The spec clarification and FR-014: failure is logged safely and invisible to the
caller (NFR-MAIL-005, NFR-LOG-003). The recipient address is omitted because the trace id
correlates the failure with the recovery event, which already identifies the user without putting
an email address in the log.

The same rule covers a token-generation failure that can only happen for an existing, enabled
account (for example an unwritable key ring): `PasswordRecovery` catches non-database exceptions
from `GeneratePasswordResetTokenAsync`, logs one `Warning` `PasswordResetTokenFailed` event
(exception type, UTC, trace/span ids) and returns no ticket, so the caller still gets `204`.
Database exceptions still yield `503`, which is identical for every address because the lookup
precedes any account-specific step.

**Alternatives considered**: Answering `503` on delivery failure was rejected by the clarification
(it would reveal account existence). Logging the exception message was rejected because SMTP server
replies can echo addresses or credentials.

## 7. Status codes and error contract

**Decision**:

| Endpoint | Condition | Response |
|---|---|---|
| forgot-password | Well-formed request (existing, unknown, disabled, token generation or delivery failed) | `204 No Content`, no body |
| forgot-password | Not JSON, malformed, missing/blank/invalid `email` | `400 The request is invalid.` |
| both | Not ready / `DbException` / `DbUpdateException` | `503 The service is not ready.` |
| reset-password | Not JSON, malformed, missing/blank field, invalid email format | `400 The request is invalid.` |
| reset-password | Invalid, altered, other-account, expired or already-used token; unknown email; disabled account | `401 Invalid or expired reset token.` (no `WWW-Authenticate`) |
| reset-password | Valid token, new password violates policy | `400 The password does not satisfy the password policy.` |
| reset-password | Success | `204 No Content`, no body, no cookie change |

**Rationale**: SRS §34.1 (*Token inválido → 401*, *Request inválido → 400*, success 200/201/204,
*503*) settles the codes by precedence, and the refresh endpoint already answers `401` for an
unusable token on an anonymous endpoint. One fixed `401` for every token/account failure satisfies
FR-008 (unknown, disabled and invalid are indistinguishable). Request validation happens before
any lookup, so `400` is independent of account existence (FR-001). Details reuse the existing
strings except the one new token message.

**Alternatives considered**: `200` with a generic message body for forgot-password was equivalent
but adds a body to keep identical; `204` matches logout and change-password. `400` for an invalid
reset token was rejected as contrary to SRS §34.1. `202 Accepted` is not in the SRS list.

## 8. Reset transaction and session revocation

**Decision**: `PasswordRecovery.ResetAsync` runs in one `IsolationLevel.Serializable` transaction:
`FindByEmailAsync` (Identity normalization) → unknown or `!IsEnabled` → `InvalidToken` →
`ResetPasswordAsync` → map `InvalidToken` → `InvalidToken`, `Password*` → `InvalidNewPassword`,
other → `Invalid` (rollback) → revoke every active family of the user with the new reason
`PasswordReset` (no family kept) → commit → log. Lockout fields are not read or changed.

**Rationale**: FR-010 (one outcome, all families, failure revokes nothing) and the persistence edge
case, using the same transaction pattern as `UserAdministration.SetEnabledAsync` and Phase 5. The
serializable transaction takes SQLite's write lock first, so two concurrent resets with one token
run one after the other: the second reads the stamp rotated by the first and gets `401` (edge case:
at most one success). Disabled accounts are refused like an invalid token (spec assumption, FR-008).

**Alternatives considered**: Resetting first and revoking afterwards was rejected (FR-010).
Keeping the caller's session was rejected: a reset has no authenticated caller and US3 requires all
sessions to end.

## 9. Shared revocation helper

**Decision**: Extract the "revoke the user's active families" loop, now needed a third time, into
one internal static helper in `Infrastructure/Sessions` (`SessionFamilyRevocation.RevokeActiveAsync(
context, userId, now, reason, keepFamilyId?)`) that runs inside the caller's transaction and
returns the revoked count. `PasswordRecovery` uses it; `UserAdministration` and `PasswordChange`
switch to it with unchanged behavior, covered by their existing Phase 3–5 tests.

**Rationale**: Constitution IV prefers less code; three copies of the same state transition would
drift. The helper is a function over the existing context, not a repository or service, and has
three current consumers.

**Alternatives considered**: A third copy was rejected for drift risk. A new injected service or
port was rejected as unnecessary abstraction.

## 10. Request shapes and email handling

**Decision**: `ForgotPasswordRequest(email)` and `ResetPasswordRequest(email, token, newPassword)`
validated like `LoginRequest`: JSON content type, non-blank fields, `EmailAddressAttribute` on the
email. The emailed token is Identity's token encoded with `WebEncoders.Base64UrlEncode` (UTF-8);
reset decodes it, and a decoding failure is `InvalidToken`. Lookups use `FindByEmailAsync`, the
normalizer used by login and user administration (FR-004).

**Rationale**: Identity tokens contain `+`, `/` and `=`, which mail clients may wrap or alter; a
base64url value is one copy-safe word. Decoding errors fold into the same `401`, so they reveal
nothing.

**Alternatives considered**: Sending the raw token was rejected for copy-paste fragility. A link
was rejected because no frontend exists (spec assumption).

## 11. Security event logging

**Decision**: Four `LoggerMessage` events, all with UTC time from `TimeProvider` and `Activity`
trace/span ids: `PasswordResetRequested` (`Information`, user id) after a token is issued;
`EmailDeliveryFailed` and `PasswordResetTokenFailed` (`Warning`, §6); `PasswordReset` (`Information`, user id, revoked family
count). No event for unknown or disabled accounts, and none contains a token, password, hash,
stamp, email body or SMTP secret.

**Rationale**: FR-017, SRS NFR-LOG-002 (*password reset exitoso*, *sesiones revocadas*),
NFR-LOG-003/004.

**Alternatives considered**: Logging the requested email for unknown accounts was rejected: it
records attacker-supplied PII without a requirement.

## 12. Verification approach

**Decision**:

- **Integration** (existing `AuthenticationApiFactory`): the factory now supplies
  `DataProtection__KeysPath` (temporary directory from `Phase1TestResources`) and dummy `Smtp__*`
  settings, and replaces `IEmailSender` with a capturing fake by default. Scenarios cover the forgot
  matrix, every token rejection, policy, success, revocation, concurrency, trigger-injected
  persistence faults (the Phase 5 technique), expiry (§2), and restart on the same SQLite file and
  key directory, plus a negative control with a different key directory.
- **Real adapter, no server**: one scenario keeps the real `SmtpEmailSender` and points it at a
  local port that was just bound and released, so connection is refused deterministically; it
  proves the generic `204`, the safe `Warning` event and the absence of the token and SMTP password
  from logs.
- **Unit**: `SmtpOptions` validation and MIME message construction.
- **Acceptance**: `tests/acceptance/phase-6.sh` adds a disposable SMTP sink through a test-only
  override `tests/acceptance/compose.mail-sink.yml` (`axllent/mailpit:v1.31.1` pinned by digest
  `sha256:98b916bd3c8d61f7633a52d3ea2f58d00620cb01ca57ab59edde68c347a95365`, published 2026-09-05)
  and reads the message through Mailpit's HTTP API. It proves a token survives
  `docker compose restart`, `up --force-recreate` and `down -v` + `up`; then runs `phase-5.sh`
  (which chains Phases 4–1). Because the container runs as a different non-root UID and the host
  has no root, `phase-6.sh` sets the key-ring owner and mode `0700` (and removes the directory at
  teardown) by running the auth-api image itself as root; Phase 1–5 scripts export disposable
  `AUTH_SMTP_*` values and a world-accessible key directory like their existing data directory.

**Rationale**: NFR-001/002, Technical Constraints §22.4 (fake sender in the normal suite; real SMTP
only where a test server is configured), Constitution VI and VII (destructive teardown only in a
disposable environment), Roadmap §12.6. The sink exists only in the acceptance override, so the
production `compose.yml` keeps its functional services and no permanent service is added.

**Alternatives considered**: A mail sink in `compose.yml` was rejected (permanent service). An
in-script SMTP listener was rejected as fragile hand-written protocol code. Exposing the token
through a test endpoint was rejected as a production backdoor. An external SMTP account was
rejected by TC §22.4.

## 13. Phase 5 divergence found during planning (resolved before implementation)

Planning found that the merged Phase 5 implementation did not count an incorrect current password
toward Identity lockout, contradicting Phase 5 `research.md` §3 and SRS NFR-SEC-BF-001. Per
Constitution II it was corrected in Phase 5, not absorbed here: the fix `[Phase 5] Fix: count an
incorrect current password as a failed attempt` (PR #6) is merged into `main` and integrated into
this branch. Phase 6 neither depends on that behavior nor changes it (the §9 helper refactor touches
only the revocation loop), so no Phase 6 decision above changes.
